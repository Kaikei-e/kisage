# 0001: LKAL葉パス射影と観測の直和型（存在の3値 Unknown / Absent / Present とノード種別 Leaf / Record / Opaque の分離）の採用

## コンテキスト

kisage は [LKAL](https://github.com/Kaikei-e/LKAL) 文書を望ましい状態の基準として読み込み、実環境の設定ファイル等を観測して差分のみを条件付きで適用する Reconciler である。この目的を達成するためには、次の3つの課題をデータモデル上で解決する必要がある。

1. **未宣言兄弟パスの保護と部分状態管理**:
   LKAL の `Equal` をルートの `Record` 全体にそのまま適用すると、実環境に存在する「宣言外の兄弟パス」まで不一致と判定されてしまう。また、宣言内の空 `Record`（`{}`）を実環境へそのまま上書きすると、実環境にある未宣言の子孫フィールドを暗黙に消去してしまう危険がある。一方で、管理していたすべての葉パスを退役（`prune`）させるためには、空のルート宣言文書自体は表現できなければならない。
2. **観測失敗（Epistemological）と表現不能（Ontological）の区別**:
   LKAL は `null` を持たず、`List` は同種のスカラー要素のみに限定され、`Int` と `Decimal` を厳格に区別する。そのため将来 JSON 等を対象とする Provider では、「I/O 失敗や権限不足により存在自体が不明な状態」とは別に、「実環境に値が存在することは確認できたが、LKAL の葉へ損失なく写像できない状態（`null`、オブジェクト配列、異種リスト等）」が生じる。これらを単一の `Unknown` に混同すると、停止理由と回復手順が曖昧になる。
3. **中間 `Record` の生成・保持と Frame Condition の定義**:
   多段の葉パス `/a/b/c` を新規作成する際には中間 `Record`（`/a`, `/a/b`）の暗黙生成が必要になり、逆に最後の葉を削除した際には LKAL の仕様上ブロックが空のまま残る。したがって「変更対象以外の構造情報も一切変化しない」という素朴な Frame Condition は成り立たない。

## 決定

LKAL 文書をスカラーおよび `List` を値とする葉パス集合 $D = \mathrm{Paths}(d)$ に射影して照合し、宣言側の非ルート空 `Record` を `K102` で拒否（空ルート $D = \varnothing$ と観測側の空 `Record` は許可）した上で、実環境の観測を存在の3値とノード種別を分離した `Observed = Unknown | Absent | Present(Leaf | Record | Opaque)` として扱い、変更対象葉以外の既存葉値と到達可能性を保存する。

### 1. 葉パス射影関数 $D = \mathrm{Paths}(d)$ と LKAL 境界
- 宣言文書 $d$ に含まれるパスのうち、値がスカラー（LKAL の `String`・`Int`・`Decimal`・`Bool`・`Enum`・`Quantity`・`Ref`）または `List` である葉パスの集合を $D = \mathrm{Paths}(d)$ と定義する。`Record` はその子へ再帰的に射影する。
- `List` の要素は個別パスで管理せず、順序を保った1つの葉値として比較・置換する。
- 値の等価判定には LKAL の `Equal` をそのまま用いる。`Record` の順序は無視、`List` の順序は有意、`Int` と `Decimal` は別型、`Quantity` は数値表現と単位の組で比較し、Provider 側での暗黙の単位換算や型変換は行わない。`Ref` は参照パスの不透明リテラル値として比較し、秘密値の外部解決は行わない。
- プログラムから受け取った `lkal.Value` も LKAL 文書の妥当性条件で検査し、Go の型で構築できることだけでは有効な入力とみなさない。

### 2. 空 `Record` の非対称規則（`K102`）
- **宣言側の非ルート空 `Record`**: 宣言文書 $d$ 内の非ルート空 `Record` は、子孫の暗黙削除を防ぐため入力検査エラー `K102: EmptyRecordNotSupported` として拒否する。
- **宣言側の空ルート文書**: 空のルート文書は $D = \varnothing$ として許可する。全管理葉の退役を表すために必要である。
- **観測側の空 `Record`**: 実環境（対象ファイル）に存在する空 `Record` は正常な `Present(Record)` として観測し、`K102` の対象とはしない。

### 3. 観測の直和型（存在の3値とノード種別の分離）
各パスおよびその真の祖先パスについて、存在の3値とノードの種類を次の直和型で表現する。

```text
Observed = Unknown(reason) | Absent | Present(Node)
Node     = Leaf(lkal.Value) | Record | Opaque(reason)
```

- `Unknown(reason)`: 読み取り失敗等により存在自体が不明。欠落した観測を `Absent` と補完してはならない。
- `Absent`: 実環境に存在しないことが確認できた状態。
- `Present(Leaf(v))`: LKAL のスカラーまたは `List` として損失なく表現できた葉値。
- `Present(Record)`: 空または非空の `Record` 節。
- `Present(Opaque(reason))`: 存在は確認したが LKAL の葉へ損失なく写像できない値（JSON の `null`、オブジェクト配列、範囲外数値等）。

### 4. 構造保護と中間 `Record` の規則
- 対象パスが `Record` または `Opaque` の場合、あるいは真の祖先パスが `Leaf` または `Opaque` の場合、`Set` および `Delete` を拒否する（`StructureConflict` / `K202` または `Unrepresentable` / `K302`）。
- 対象または真の祖先が `Unknown` の場合は観測不能（`ObservationUnavailable` / `K301`）として変更を保留する。末端が `Absent` であっても真の祖先の保護検査を省略しない。
- 葉の作成に必要な、存在しない中間 `Record` の生成を許可する。一方で、既存 `Record` の `Leaf` 化、既存葉を破壊する祖先置換、および最後の葉を削除した後に残る空 `Record` の自動清掃は禁止する。保存対象は「変更対象葉以外の既存葉値、およびその到達可能性」と定義する。

## 根拠（調査結果・出典）

1. **内部不変条件（子孫非破壊と全葉退役の両立）**:
   葉パス射影 $\mathrm{Paths}(d)$ において空の非ルート `Record` `{}` は葉を生成しないため、これを許容すると「空 `Record` に設定して子孫を消す意図」と「何も宣言していない状態」が射影後に区別できなくなる。非ルート空 `Record` を `K102` で拒否しつつルートのみ $D = \varnothing$ を認めることで、部分管理の安全性と全葉退役の表現力を矛盾なく両立できる。
2. **LKAL コア仕様との整合**:
   LKAL の `value.go` および設計原則では、`List` は同種スカラーのみ、`null` は存在せず、構文木上のパス削除は最後の要素を消しても空ブロックを残す仕様となっている。観測側に空 `Record` が残ることは LKAL ファイル Provider の正常な帰結であり、`Present(Record)` として扱う必要がある。
   - [LKAL value.go](https://github.com/Kaikei-e/LKAL/blob/main/value.go)
   - [LKAL 設計原則 (PRINCIPLE.md)](https://github.com/Kaikei-e/LKAL/blob/main/docs/PRINCIPLE.md)
3. **参考（本決定の根拠ではない）: 宣言的インターフェースにおける目標と機構の分離**:
   DMI は既存 GUI を宣言的プリミティブへ置き換えるインターフェースにより、成功率の相対67%改善と操作ステップ43.5%削減を報告する。これは GUI 実験の値であり、設定ファイルに対する kisage の期待効果へ転用しない。目標（宣言）と機構（観測・収束）を分離するという設計上の参考にとどめる。
   - [From Imperative to Declarative: Towards LLM-friendly OS Interfaces for Boosted Computer-Use Agents (arXiv:2510.04607v2)](https://arxiv.org/abs/2510.04607v2)

## 検討した代替案

- **A. LKAL の `Record` 全体をそのまま比較・置換する**:
  不採用。未宣言の兄弟パスが常に不一致となり、ファイル全体を再生成するのと変わらなくなるため。
- **B. LKAL で表現できない値（`null` 等）を `Unknown` に含める**:
  不採用。`Unknown` は「再試行や権限付与で解消しうる観測失敗（`K301`）」であるのに対し、表現不能な値は「存在と構造が確定した上での写像不能（`K302`）」であり、原因も対処も異なるため。
- **C. 最後の葉を削除した際、暗黙に作成した中間 `Record` も自動で再帰削除する**:
  不採用。「どの空 `Record` が kisage によって暗黙作成されたか」の所有履歴を中間節ごとに追跡する必要が生じ、LKAL の「最後の要素を削除してもブロックを残す」仕様とも衝突するため。

## 影響とトレードオフ

- **得るもの**:
  - 未宣言の兄弟葉および `Opaque` な兄弟フィールドを壊さずに、許可された葉パスだけを安全に更新できる。
  - Lean 4 での `Observed` 型と構造保護定理（定理2・定理4）が直和型のパターンマッチとして簡潔に定式化できる。
- **失うもの・引き受けるリスク**:
  - `List` の特定要素だけの部分編集は表現できず、リスト全体の置換となる。
  - 葉の削除後に空の `Record` が残るため、`Record → 葉` の構造変更は自動で行えず、別途管理手順が必要となる（版間の構造移行規則は [[0003]] の「版間の構造移行（葉↔Record）の非自動化」で規定）。
