# 0002: 共有所有ストア（σとσ_Aの分離）・4種操作権限（Set/Delete/Own/Resolve）・3層保証境界

## コンテキスト

[[0001]] で定義した葉パス射影モデルの上で、複数の実行主体（Actor）や人間が同一の設定ファイル（Resource）に関わる環境を考える。このとき、次の3つの要件を同時に満たす必要がある。

1. **マルチ Actor 間の衝突検出と無関係な所有の分離**:
   もし所有記録ストア $\sigma$ が自 Actor のエントリしか持たなければ、別 Actor が作成したパスを「未所有の既存値」と誤認して乗っ取りや二重所有が発生する。逆に、照合対象集合 $M$ を全 Actor の共有ストア全体の $\mathrm{dom}(\sigma)$ にしてしまうと、別 Actor が無関係なパスを1つでも所有しているだけで毎回 `OwnershipConflict` が発生し、収束条件も永遠に成立しない。
2. **削除権の根拠（`Origin`）の正確な履歴定義**:
   「自分が新規作成したと確認された葉だけを削除する」という保守的削除原則を守るには、新規作成（`Created`）と既存値採用（`Modified`）を区別する必要がある。さらに、新規作成後に同じ Actor が値を更新しても削除権は維持されるため、「`Created` ならば現在の `LastApplied` を不在から作成した」という素朴な命題は不変条件にならない。
3. **権限境界と保証範囲の明確化**:
   通常の作成・更新・採用・管理解除に必要な権限と、外部ドリフトを明示的に追認・放棄する権限が同一であると、通常のエージェントがドリフト停止を勝手に解除できてしまう。また、kisage 自身が論理的に保証できることと、OS やホスト環境が担保すべき境界を分離して定義する必要がある。

## 決定

全 Actor の所有記録を直列化する共有ストア $\sigma$ から自 Actor 分の射影 $\sigma_A$ を切り出して照合対象を $M_A(d, \sigma) = D \cup \mathrm{dom}(\sigma_A)$ とし、単一所有者排他（同一・親子重複および `Pending` 予約を含む）と所有開始時からの作成履歴を表す `Origin = None | Created | Modified` を定義するとともに、パース済みセグメント列上の4種権限（`Set / Delete / Own / Resolve`）および3層の安全保証境界（Logical Frame / Provider Preservation / Execution Boundary）を定める。

### 1. 共有所有ストア $\sigma$ と自 Actor 射影 $\sigma_A$
- 所有権のキーは `(ResourceID, PathSegments)` とする。`Resource` は Provider 種別、固定された管理ルート、および対象ファイルへの束縛を含む。同一の物理対象を別名・ハードリンク・別ストアで重複登録することを禁止する。単一ファイル Provider ではハードリンク自体も拒否する。
- v0.1 は1つの信頼されたランタイムを通して全 Actor の所有記録 $\sigma$ を直列化する。共有ストア $\sigma$ のうち `Manager == A` の部分を $\sigma_A$ と定義し、Actor $A$ の1周回の照合対象パス集合を次式で定める。

$$M_A(d, \sigma) = D \cup \mathrm{dom}(\sigma_A)$$

- 別 Actor の宣言外所有パス（$\mathrm{dom}(\sigma) \setminus \mathrm{dom}(\sigma_A)$ のうち $D$ と重ならないもの）は照合対象に加えず、無関係な所有を理由に衝突を報告しない。
- ただし、$D$ に含まれるパスと別 Actor 所有パスが**同一、または祖先・子孫として重なる場合**は `OwnershipConflict`（`K201`）を診断し、そのパスの取得・変更を許可しない。値が一致していても共有所有（二重所有）にはしない。未完了の `Pending` 予約も排他的な所有として扱う。診断が当該モード全体を止める `Blocker` か、独立したモード外の `Deferred` かは [[0003]] の SelectMode に従う。
- 同じ `(Actor, Resource)` に対する宣言は1つの完全な意図集合として扱う。部分集合の宣言を交互に適用すると他方の所有葉が退役扱いになるため、複数の意図を管理する場合は事前に宣言を統合する。宣言ファイル単位の独立所有は v0.1 では提供しない。

### 2. 所有状態 `OwnerEntry` と `Origin` の履歴不変条件
各所有エントリは以下の状態を持つ。

```text
OwnerEntry = { Manager, Origin, LastApplied?, Pending? }
Origin     = None | Created | Modified
```

- `Origin = None`: 新規所有の `Intent`（`Pending`）記録中のみ有効。確定所有としては存在しない。
- `Origin = Created`: **その所有セッションの開始時点において自 Actor による `Absent → Present` の適用完了が確認され、かつその後の遷移がすべて自 Actor の正当な更新である**ことを表す。新規作成後に値を更新しても `Created` を維持する。
- `Origin = Modified`: 既存の未所有値の一致採用、クラッシュ回復時の作成帰属未確認による降格、または明示的な `adopt` による所有であり、自動削除権を持たない。
- **値同値 Provider における ABA の限界**: 値の同値性（`Equal`）のみを条件とする Provider は、外部による「削除→同値再作成（ABA）」を識別できない。`Created` は現在の値の物理的な出自までは保証しない。

### 3. パース済みセグメントによる Scope と4種の操作権限
- `Scope` は文字列の前方一致ではなく、パース済みパスセグメント列と操作種別で判定する。
- 操作権限は `Set` / `Delete` / `Own` / `Resolve` の4種を区別する。
  - 新規作成・値更新：`Set + Own`
  - 既存一致値の採用・退役 `Modified` の管理解除・不在が確認された退役 `Created` の記録削除・クラッシュ回復の保存：`Own`
  - 退役 `Created` の環境削除（`prune`）：`Delete + Own`
  - 明示的なドリフト追認・所有放棄（`adopt` / `release`）：`Own + Resolve`（`Resolve` は通常の `Own` からは導出されず、ホストが別途付与する）

### 4. 3層の安全保証境界と信頼の根
安全保証を以下の3層に分離する。

1. **Logical Frame（第1層）**: 通常計画と回復の変更は $M_A(d, \sigma)$ 内、明示解消は指定された1パス内に収まり、それぞれ必要な Scope を満たす（Lean 4 証明＋Go との DRT）。
2. **Provider Preservation（第2層）**: 構造保護、対象外の葉値保存、ロック下の条件再検査、宣言した永続化手順（適合性テスト・PBT・障害注入）。
3. **Execution Boundary（第3層）**: 信頼情報と書き込み経路の保護、直接編集の遮断（OS 権限・サンドボックス・ホスト設定の責務であり、kisage 単独の保証範囲外）。

- **信頼の根**: Scope、Actor 注入元、Resource 登録、所有ストアとその永続化、ロックと親ディレクトリ、Provider、固定された LKAL 実装。CLI の任意の `--actor` 引数や MCP ツール引数の自己申告は認証として受け入れず、ホスト設定または保護された実行環境が Actor を束縛する。

## 根拠（調査結果・出典）

1. **内部不変条件（削除責任の一意性と収束独立性の両立）**:
   複数 Actor による共有所有を認めると、一方の Actor が宣言から外した際に削除すべきか残すべきかの責任が曖昧になり、また一方のクラッシュ回復と他方の所有状態が干渉する。単一所有者排他（同値でも別 Actor 所有なら衝突停止）と $\sigma_A$ による照合範囲の分離を組み合わせることで、削除責任の一意性と無関係な Actor 間の非干渉を同時に満たすことができる。
2. **Kubernetes Server-Side Apply (SSA) との意味論的比較**:
   SSA は複数 applier が同一値を設定した場合に所有権を共有し、最後の所有者がフィールドを外すと削除またはデフォルト値へ戻す。kisage は削除の保守性を最優先するため、共有所有を採らず、`Origin = Created` 以外は自動削除しない設計を選択した。
   - [Kubernetes Server-Side Apply Specification](https://kubernetes.io/docs/reference/using-api/server-side-apply/)
3. **MCP における stdio トランスポートの認可境界**:
   MCP 仕様において stdio トランスポートは HTTP ベースの認可フローを用いず、ホスト環境から資格情報・実行文脈を与える前提となっているため、Actor 束縛は第3層（ホスト側設定）の責務となる。
   - [Model Context Protocol Specification — Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

## 検討した代替案

- **A. Actor ごとに独立した所有ストアファイルを持ち、共有ストアを持たない**:
  不採用。別 Actor が所有するパスが「未所有の既存値」に見えてしまい、同値の二重採用や削除権の衝突を検出できなくなるため。
- **B. 同値であれば複数 Actor の共有所有を許可する（SSA 方式）**:
  不採用。どちらの Actor が最初に `Absent` から作成したか（`Origin = Created` vs `Modified`）の帰属が共有解消時に曖昧になり、保守的削除の不変条件が複雑化するため。
- **C. `Resolve` 権限を分けず、`Own` 権限だけでドリフト解消も許可する**:
  不採用。通常の `apply` を実行するエージェントが、人間に無断で `adopt` / `release` を呼び出して外部ドリフト停止を突破できてしまうため。

## 影響とトレードオフ

- **得るもの**:
  - 同一ファイル内の異なるパスを複数の Actor が管理しても、パスの重複（同一・親子）がない限り互いの収束や `Match_A(d)` を妨げない。
  - 「`Origin = Created` ならば自 Actor が不在から作成を開始し正当に更新してきた」という履歴不変条件を、プロトコル状態機械上の帰納的不変条件として証明する対象にできる（証明は [[0005]] の Phase 1 ゲートで行い、本 ADR の時点では未証明）。
- **失うもの・引き受けるリスク**:
  - 複数の Actor がまったく同じ葉パスに同じ値を宣言して協調管理するユースケースは `OwnershipConflict` となり利用できない。
  - 第3層（ホスト設定やファイル権限）が破られ、エージェントが直接所有ストアや対象ファイルを書き換えた場合は保証が成立しない。
